# payments-api

API платежей для онлайн-школы: тарифы, создание платежа (карта, СБП, рассрочка), идемпотентность
по заголовку `Idempotency-Key` и вебхук банка со сменой статусов и проверкой подписи.

Стек: Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 (async) + asyncpg, PostgreSQL 17, Alembic,
pytest + httpx. Менеджер пакетов: [uv](https://docs.astral.sh/uv/getting-started/installation/).

## Быстрый старт (Docker)

Нужен только Docker.

```bash
docker compose up --build
```

Что произойдёт: поднимется Postgres, применятся миграции, создадутся тарифы, API станет доступен на
http://localhost:8000 (интерактивная документация: http://localhost:8000/docs).

Секрет подписи вебхуков в compose по умолчанию `change-me`. Это значение только для разработки.
Задать свой: `WEBHOOK_SECRET=мой-секрет docker compose up --build`.

## Локальная разработка (uv)

```bash
uv sync                          # зависимости (создаст .venv)
docker compose up -d db          # только база, порт на хосте 5433
cp .env.example .env             # в PowerShell: Copy-Item .env.example .env
uv run alembic upgrade head      # миграции
uv run --env-file .env uvicorn app.main:create_app_from_env --factory --reload
```

Порт базы на хосте 5433 (а не 5432), чтобы не конфликтовать с локальным Postgres.

Переменные окружения:

| Переменная       | Обязательна | По умолчанию                                                  |
|------------------|-------------|---------------------------------------------------------------|
| `DATABASE_URL`   | нет         | `postgresql+asyncpg://payments:payments@localhost:5433/payments` |
| `WEBHOOK_SECRET` | **да**      | нет. Без неё приложение не запускается                          |

## Тесты и проверки

```bash
docker compose up -d db          # тестам нужен Postgres
uv run pytest
uv run ruff check
uv run ruff format --check
```

Тесты сами создают базу `payments_test` на том же сервере, накатывают на неё миграции (и проверяют
откат) и очищают платежи между тестами. Рабочая база `payments` не затрагивается: тесты отказываются
запускаться на базе, имя которой не заканчивается на `_test`. Секрет вебхука тестам не нужен.

Те же проверки выполняет GitHub Actions на каждый push (`.github/workflows/ci.yml`).

## Эндпоинты

| Метод и путь         | Что делает                                                              |
|----------------------|-------------------------------------------------------------------------|
| `GET /tariffs`       | 200, список тарифов `[{id, title, price}]`                              |
| `POST /payments`     | 201 платёж создан; 200 если платёж с таким `Idempotency-Key` уже есть   |
| `GET /payments/{id}` | 200 платёж; 404 если нет                                                 |
| `GET /payments`      | 200 список; необязательные фильтры `?email=...&status=...`              |
| `POST /webhooks/bank`| Смена статуса. 200 `{"result":"ok"}`; 404; 409 `{"error":"invalid_transition"}`; 401 при неверной подписи |

Тарифы: `basic` 9 900 ₽, `standard` 19 900 ₽, `premium` 29 900 ₽. Все суммы в API и базе
целые числа в копейках: 19 900 ₽ это `1990000`. Промокод `KVITTO10` даёт скидку 10%, регистр не важен.

Статусы и допустимые переходы: `pending → succeeded`, `pending → failed`, `succeeded → refunded`.
Остальные переходы запрещены.

## Примеры запросов

Примеры для bash (Linux, macOS, Git Bash). В Windows PowerShell вместо `curl` пишите `curl.exe`
или используйте PowerShell-вариант вебхука ниже.

```bash
# Тарифы
curl http://localhost:8000/tariffs

# Платёж в рассрочку на 3 месяца с промокодом и ключом идемпотентности
curl -X POST http://localhost:8000/payments \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1001" \
  -d '{"tariff_id":"standard","email":"student@example.com","method":"installment","installment_months":3,"promo_code":"kvitto10"}'
# 201: amount 1791000, discount 199000, schedule [597000, 597000, 597000]
# Тот же запрос ещё раз: 200 и тот же платёж, второй не создаётся.

# Платёж по id и список с фильтрами
curl http://localhost:8000/payments/1
curl "http://localhost:8000/payments?status=pending&email=student@example.com"
```

### Вебхук банка

Заголовок `X-Signature` содержит HMAC-SHA256 от **сырых байтов тела запроса** с секретом
`WEBHOOK_SECRET`, в виде hex-строки в нижнем регистре, без префикса.

bash:

```bash
BODY='{"payment_id":1,"status":"succeeded"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "change-me" | awk '{print $NF}')
curl -X POST http://localhost:8000/webhooks/bank \
  -H "Content-Type: application/json" -H "X-Signature: $SIG" -d "$BODY"
# {"result":"ok"}
```

PowerShell:

```powershell
$body = '{"payment_id":1,"status":"succeeded"}'
$hmac = New-Object System.Security.Cryptography.HMACSHA256 (,[Text.Encoding]::UTF8.GetBytes("change-me"))
$sig = ($hmac.ComputeHash([Text.Encoding]::UTF8.GetBytes($body)) | ForEach-Object { $_.ToString("x2") }) -join ""
Invoke-RestMethod http://localhost:8000/webhooks/bank -Method Post -Body $body `
  -ContentType application/json -Headers @{ "X-Signature" = $sig }
```

Без подписи или с неверной подписью ответ 401. Повторная отправка того же вебхука даёт 409.

## Структура проекта

```
app/
  enums.py        статусы и методы оплаты (только стандартная библиотека)
  domain.py       чистая бизнес-логика: скидка, график рассрочки, таблица переходов
  models.py       таблицы SQLAlchemy
  schemas.py      схемы запросов и ответов Pydantic
  db.py           движок, сессии, создание тарифов при старте
  config.py       чтение переменных окружения
  security.py     проверка подписи вебхука
  main.py         сборка приложения
  routers/        tariffs.py, payments.py, webhooks.py
migrations/       Alembic (async)
tests/            pytest; conftest.py готовит тестовую базу и клиента
```

Направление импортов: `enums` ← `domain` ← `models`/`schemas` ← `routers`. Модули `enums` и `domain`
не знают о FastAPI, Pydantic и SQLAlchemy, поэтому бизнес-правила тестируются без базы.
Слоёв service/repository нет: роутеры работают с сессией напрямую.

## Принятые решения

Места, где ТЗ допускает несколько трактовок, и выбранный вариант.

**Деньги**
- Только `int` в копейках, без `float` и `Decimal`. Скидка: `price * 10 // 100` (округление вниз).
  Сейчас цены делятся нацело, но формула не зависит от этого.
- `amount`: итоговая сумма к оплате, `discount`: скидка в копейках (`0`, а не `null`, без
  промокода). Всегда `amount + discount = цена тарифа`. Сумму и скидку считает сервер: если клиент
  пришлёт их в теле, поля игнорируются.
- `schedule` не хранится в базе, а считается из `amount` и срока. Лишние копейки идут в первые
  платежи. Если алгоритм графика изменится, у старых платежей график пересчитается по-новому.

**Создание платежа**
- `tariff_id` строка-слаг (`basic`, `standard`, `premium`). Неизвестный тариф: 422.
- Промокод: регистр не важен. Неизвестный код, пустая строка и код с пробелами по краям: 422.
  `null` или отсутствие поля: без скидки.
- Для `installment` срок обязателен и может быть только 3, 6 или 12. Для `card` и `sbp` срок
  передавать нельзя: 422.
- Сумма, скидка и график в ответах всегда целые числа.

**Идемпотентность**
- Платёж с известным ключом возвращается как есть (200), тело запроса не сравнивается: другое тело
  с тем же ключом вернёт исходный платёж. Сравнение тел можно добавить позже.
- Порядок проверок: валидация схемы (422), затем поиск по ключу, затем проверка тарифа и промокода.
  Поэтому повтор с известным ключом вернёт исходный платёж даже при неизвестном тарифе в теле.
- Пустой ключ или длиннее 255 символов: 422. Неудачный запрос (например, 422 из-за промокода) ключ
  не занимает.
- Гонка двух одновременных запросов решается уникальным ограничением на колонку ключа: проигравший
  откатывает транзакцию, перечитывает платёж и возвращает его с кодом 200.
- Ключ глобальный, не привязан к клиенту (авторизации в задаче нет).

**Вебхук**
- Повторный вебхук с тем же статусом: 409 (переход в тот же статус не разрешён таблицей). Вебхук со
  статусом `pending`: тоже 409.
- Статус меняется одним условным `UPDATE ... WHERE status IN (допустимые)`. Два одновременных
  вебхука не могут оба сработать.
- Порядок проверок: подпись (401), затем валидация тела (422), 404, 409. Исключение: тело, которое
  вообще не JSON, FastAPI отвергает с 422 до проверки подписи.
- Ответ 409 имеет ровно тело `{"error": "invalid_transition"}`, а не стандартный `{"detail": ...}`.
- `WEBHOOK_SECRET` обязателен, без него приложение не стартует.

**Прочее**
- Для `GET /payments/{id}` и `payment_id` в вебхуке допустимы числа от 1 до 2 147 483 647 (размер
  `id` в базе), иначе 422. `GET /payments/999` для существующего диапазона: 404.
- `GET /payments`: фильтр по `email` точный (с учётом регистра), сортировка по `id`, пагинации нет.
- `created_at` хранится и отдаётся в UTC.
- Тарифы создаются при старте через `INSERT ... ON CONFLICT DO NOTHING`: повторный запуск ничего не
  дублирует. Изменение цены в коде существующие тарифы не обновит. Сумма платежа хранится в самом
  платеже, поэтому старые платежи при смене цены не меняются.
- Статус и метод оплаты хранятся строкой с `CHECK`, а не нативным enum Postgres: такие поля проще
  менять в миграциях.
- База: PostgreSQL и асинхронная SQLAlchemy (выбор сверх минимума ТЗ ради блокировок и ограничений
  уникальности, на которых построены идемпотентность и смена статуса).

## Известные ограничения

- Нет авторизации: любой клиент может читать платежи и использовать любой `Idempotency-Key`.
  Идентификаторы платежей последовательные, их легко перебирать.
- Нет пагинации в `GET /payments`.
- Реальные банки повторяют вебхуки при сомнении в доставке. Здесь повтор того же статуса даёт 409
  по таблице переходов из ТЗ. В реальной системе стоило бы отвечать 200 на безопасный повтор.
- Миграции запускаются при каждом старте контейнера. Для одного экземпляра это нормально; для
  нескольких реплик их лучше вынести в отдельный шаг.
- Секрет `change-me` в `compose.yaml` только для разработки. Контейнер работает от root.
- Нет логирования и метрик.
